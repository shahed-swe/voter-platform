## 2. Fix: GPS capture in the canvass form

`client/src/components/canvassing/CanvassFormModal.jsx` — the "GPS ক্যাপচার" button previously
called `getCurrentPosition` with NO options (no timeout → often never fired; stale cached
positions; raw English errors; no feedback). Now:
- High-accuracy fresh fix first (`enableHighAccuracy, maximumAge:0, timeout:10s`), automatic
  fallback retry accepting a coarser/cached position (15s, maxAge 60s).
- Busy spinner + disabled button while capturing; friendly Bangla error messages per error code;
  explicit secure-origin (HTTPS) message instead of silent failure. Coords stored at 6 decimals.

## 3. Feature: ALL located voters shown as pins on /canvassing

Previously only one clicked voter appeared on the map. Now, selecting ward/voter-area in the
GeoNavigator shows a pin for EVERY voter in scope whose latest canvass has a geolocation.
- Server: `POST /api/canvassing/voter-locations` → `canvassingModel.voterLocationsByScope()`
  (`DISTINCT ON (voter_id)` latest canvass w/ lat-lng, joined voter details, scoped per political
  candidate; enforces volunteer `allowed_wards`/`allowed_voter_areas` like the voter list).
- Client: `DynamicCanvassing.jsx` fetches on scope change and re-fetches after every canvass
  submit (keyed on `listRefreshKey`); passes `voterPins` to `DynamicMap`.
- `DynamicMap.jsx`: small indigo dot per voter (name/area tooltip, click opens canvass form);
  the list-clicked voter keeps the big teardrop pin + new `FlyTo` zooms to their exact location.

## 4. Fix: building click-to-select on the map

Root cause: buildings' click action (`voters` in `map_config`) fired `onLeafClick` with
`drillStack[1].label` — but GeoNavigator-driven drills fill that entry with the generic label
`"Ward"` (see `DynamicMap.jsx` focusVillage effect), so `wardLabelToScope("Ward")` returned null
and `handleLeafClick` silently dropped the whole click. Also there was no selected-building visual.
- `DynamicCanvassing.handleLeafClick` no longer drops the click when the ward label can't be
  parsed (navigator scope already narrows the list); always sets `buildingCtx` + refreshes.
- `DynamicMap` new prop `selectedFeatureId` → clicked building painted amber (selection id is in
  the GeoJSON key to force repaint); leaf-click payload also carries `areaLabel`.
- Amber chip (top-center) shows the selected building's name/id with ✕ to clear; selection clears
  on nav change. Selected building tags subsequent canvasses (`building_feature_id` + centroid).

## 5. Building names: why "way/323082350" vs real names + crowd-sourcing fix

Buildings come from OpenStreetMap: only ~3,042 of 179,718 (1.7%) have a real name
(`geo_layers.props.building_name`); the rest only have OSM ids (`way/…`, `node/…`). The building
LINK works fine for unnamed buildings (`canvassing.building_feature_id` is TEXT).
- `CanvassFormModal` now shows the selected building (name or `#way/…`) with a Bangla hint that a
  typed name will be saved to the map.
- `canvassingModel.submit()` writes a typed building name back to
  `geo_layers.props.building_name` (only when currently empty — never overwrites curated names).
  → names accumulate from field work.

## 6. Fix: multiple voters in one building looked like "replacement"

Nothing was replaced (verified in DB: Style Point Appartment `way/263626445` has both voters).
Voters at the same building share the exact centroid coords, so pins stacked and only the top one
was visible/clickable.
- `DynamicMap.jsx`: `spreadVoterPins` memo groups pins by ~1 m cell and lays co-located groups in
  a ~7 m ring around the shared point — all voters visible + individually clickable.
- `server/src/models/urbanModel.js` `canvassedVotersForBuilding`: matched only legacy numeric
  `building_id` (NULL for OSM buildings → empty modal). Now also matches `building_feature_id`.
